# multiplat-factory

Port an app from one platform (web, iOS, Android) to the others, producing fully functional builds, with a dashboard for steering and observing the process. This is a general-purpose product for anyone, not a tool for one person's apps or machine.

## Commands

- `pnpm install` (Node >= 22.13; `.nvmrc` says 24)
- `pnpm dev` — server (4310) + dashboard (4311)
- `pnpm test` — vitest across all packages; tests tagged by toolchain skip when the toolchain is absent
- `pnpm typecheck`, `pnpm lint`, `pnpm format`
- `pnpm mpf <cmd>` — run the CLI from source: `doctor`, `setup [--yes|--dry-run]` (installs what doctor reports, asking per step), `serve`, `port <src> --to ios,android [--budget <usd>] [--core auto|always|never] [--until <stage>] [--detach] [--yes] [--web-framework <flavor>]`, `runs`, `status <run>`, `resume|rerun|answer|instruct`

## Package map (dependency direction: left never imports right)

`core` <- `llm` <- {`analyzer`, `critic`, `wasm-core`}; `core` <- `harness` <- `adapters` <- {`analyzer`, `wasm-core`}; `orchestrator` imports all of them; `server` imports `orchestrator`; `cli` imports `server`, `orchestrator`, `harness`. `dashboard` imports only the isomorphic `@mpf/core` subpaths (`schemas`, `reducer`, `stages`; no Node APIs).

## Invariants

- The orchestrator is deterministic TypeScript. LLMs produce artifacts; they never decide control flow.
- Schemas are zod-first in `packages/core/src/schemas`. Every LLM-facing schema is also exported as JSON Schema through `toJsonSchema`.
- All platform and framework knowledge lives in `packages/adapters`. Nothing else may branch on "React" or "SwiftUI".
- No hardcoded machine paths. Toolchains are discovered (`xcode-select`, `JAVA_HOME`, `ANDROID_HOME`, PATH) with overrides in `~/.mpf/config.json`.
- No user-specific defaults. Fixtures are pinned by git URL + commit in `fixtures/manifest.json`; in-house fixtures live in `fixtures/inhouse`.
- Every LLM call goes through `@mpf/llm`. Budgets are always enforced.
- Run data lives under `~/.mpf` (or `$MPF_HOME`), never in the repo.
- Events are the source of truth: the dashboard view is `applyEvents(emptyView(), log)`, and the same reducer runs in server tests.

## Adding an adapter

See `docs/ADAPTERS.md`. Implement `SourceAdapter` or `TargetAdapter` from `packages/adapters/src/types.ts`, register it in the registry, add a fixture to the matrix.

## Style

TypeScript strict, ESM, `.ts` extensions in relative imports, `import type` for types, Prettier (no semicolons, single quotes, width 100). Tests in `test/` next to `src/`.

## Gotchas

- `node:sqlite` needs Node 22.13+; on 22.11 it is behind `--experimental-sqlite`.
- macOS has no `timeout` binary; use execa timeouts.
- pnpm 12 blocks dependency build scripts by default; allow specific ones under `allowBuilds` in `pnpm-workspace.yaml` (esbuild, unrs-resolver today) only when needed.
- Agent SDK: never pass bare tool names in `allowedTools` for workers. Bare entries auto-approve the tool before `canUseTool` runs, so the sandbox policy in `packages/llm/src/permissions.ts` would be bypassed. Gate everything through `canUseTool` (and `disallowedTools` for network tools).
- Agent SDK `outputFormat` schemas must be draft-7 without a `$schema` key; the runtime rejects the 2020-12 meta-schema reference. `toJsonSchema` in `@mpf/core` already does this.
- The Agent SDK reuses the user's Claude Code login from a plain Node process; a worker turn on `claude-sonnet-5` at low effort costs roughly $0.10 because the tool definitions are cached on the first call.
- nvm keeps global CLIs per Node version: under Node 24, `claude` from the Node 22 install is not on PATH, so `mpf doctor` may report no Claude login in that shell even though the Agent SDK still works.
- Grammar WASM packs are tied to the web-tree-sitter ABI. `tree-sitter-wasms` (0.1.x) uses the legacy `dylink` section and only loads on web-tree-sitter 0.22; the analyzer uses `tree-sitter-wasm` 2.x (layout `out/<lang>/tree-sitter-<lang>.wasm`), which loads on 0.27. If a grammar fails inside `getDylinkMetadata`, it is this mismatch.
- Playwright Chromium lives outside the repo (`~/Library/Caches/ms-playwright` on macOS); install it with `pnpm --filter @mpf/analyzer exec playwright install chromium`. The observe stage degrades to "unverified" without it.
- Gradle 8.14 / AGP 8.13 run on JDK 17-24 only. A newer JDK fails inside Gradle with the bare message `java.lang.IllegalArgumentException: 27`. Homebrew's `openjdk` formula tracks the newest release (Maestro depends on it), so the harness prefers `openjdk@21` and the doctor reports out-of-range JDKs. Run `gradle --stop` after switching JDKs.
- The AndroidX train from Compose 1.12 / navigation 2.10 / lifecycle 2.11 on requires compileSdk 37 and AGP 9.1; `ANDROID_VERSIONS` in the Android template pins the last SDK-36 train. Move all of them together.
- `brew install maestro` resolves to an unrelated cask. The mobile testing tool is `brew install --formula mobile-dev-inc/tap/maestro` after `brew trust mobile-dev-inc/tap` on Homebrew 6.
- Worker budget caps come from `budgetShare` in `runWorker`; a floor of $3 protects large-prompt stages and $5 protects resumed sessions, whose long transcripts make every turn cost more (a $3 cap bought a fix worker 17 turns). Budget exhaustion is reported as `budget-exhausted` and never retried with the same cap; the test-fix loop still retests after a worker that ran out, since partial fixes are common.
- iOS: opening a custom URL scheme from outside the app (`simctl openurl`, Maestro `openLink`) shows a system "Open in …?" dialog on the simulator, and a stale dialog hides the whole app from Maestro's hierarchy. Flows and screenshots therefore navigate with the `mpf_route` launch argument or environment variable (`LaunchValues` in the scaffold); deep links stay for real use. Shut the simulator down if such a dialog is stuck.
- iOS: `simctl boot` on a booted device fails with `code=405 … current state: Booted`; the harness treats that as already booted. Device names are matched case-insensitively (`mpf-iphone`).
- Android scaffold: `rootProject.name` is the display name with Gradle's forbidden characters (`/ \\ : < > " ? * |`) removed (`gradleProjectName`); the first public-fixture port (TodoMVC Vue, spec name "TodoMVC: Vue") blocked at the scaffold three times on the colon before any generation. iOS and web derive their project and package names through `iosProjectNameFor` and `webPackageNameFor` the same way.
- Android: `am start` needs the explicit component (`-n pkg/.MainActivity`); implicit MAIN/LAUNCHER resolution by package fails on recent Android.
- Android: deep links are `mpf://<applicationId>/<screenId>` (scheme plus host in the manifest `<data>`). A scheme-only filter makes every ported app on the device claim `mpf://…`, and Maestro's `openLink` then lands on the system "Open with" chooser, which fails every flow. Uninstall stale `app.mpf.*` packages from the emulator if a chooser still appears.
- Android: a Compose `Button` exposes its label on a child accessibility node, so `assertVisible: {id, text}` never matches it, while a tagged `Text` or `TextField` carries the text itself and iOS flattens both. `compileMaestroFlow` therefore waits briefly for the direct match and falls back to `containsDescendants`; keep that when touching text assertions.
- Agent SDK: a resumed session's result reports the whole session's spend (Claude Code 2.1.277+ restores totals from the transcript). `runWorker` keeps `sessions.json` in the run directory and charges the run only for the increment; never add a resumed result's `total_cost_usd` to a run directly. `maxBudgetUsd` still caps only the call's own spend.
- Rust: Homebrew's `rustup` puts the proxies in `<brew prefix>/opt/rustup/bin` and nothing on PATH; `rustTools` in the harness looks there and in `~/.cargo/bin`. The shared core needs the `wasm32-unknown-unknown` target.
- `WebAssembly` types come from TypeScript's DOM lib; `packages/wasm-core/src/host.ts` references it with a triple-slash directive so every consumer typechecks without changing their tsconfig.
- Chicory is `com.dylibso.chicory:runtime` (1.7.5 on Maven Central; the plan's 1.4.0 is stale) and needs API 28; WasmKit 0.4.0 needs Swift 6.3 tools (Xcode 26.3+) and a deployment target of iOS 18, and compiling it adds about three minutes to the first xcodebuild. Both are pinned in `packages/adapters/src/core/`; the templates raise minSdk/deployment target only when a core is embedded.
- Android: apps targeting SDK 35+ draw edge to edge, so the status bar window (about the top 136 px on the emulator) overlaps the app and swallows taps; a header under it looks like a control that "does nothing" (a tap completes, nothing navigates). The scaffold's `AppRoot` wraps content in `safeDrawingPadding()`; keep it. Maestro runs with `--debug-output <workspace>/maestro-debug`, and failing flow cases carry a screenshot plus a hierarchy summary (`evidence`) that the fix worker reads.
- Cost is charged to the stage and the run the moment a worker returns (`ctx.chargeCost` from `runWorker`), not only when the stage ends; a killed or paused stage keeps what it spent, and the runner adds only the part of an outcome's `costUsd` that exceeds what was charged.
- Svelte scaffold: `svelte-check` needs an explicit `declare module '*.svelte'` in `src/env.d.ts` with our tsconfig, and mounting components in vitest's jsdom needs `resolve.conditions: ['browser']` or Svelte resolves to its server build and `mount` throws.
- Artifacts may be directories (an iOS `.app` bundle): `addArtifact` records `inode/directory` with the total size and no hash instead of reading them. The `report` stage depends on each target's `fix` stage (the end of that target's loop) with soft dependencies: it runs once every one of them has ended, however it ended, so a blocked target still gets its PORT.md and the run summary; a fix round that reruns a target also resets the report so it runs again at the end.
- A `custom` behavior step is a note, not a stop: the web executor (observe stage and web target) runs the typed steps around it and records the skipped description on the case, and the Maestro compiler does the same. Only a behavior made of nothing but custom steps is skipped. Prefer `openRoute` and the typed steps in the behaviors prompt so as few notes as possible remain.
- Hookless sources (most public web apps: TodoMVC uses classes and one id): `Element.sourceSelector` says how to find an element on the original app (web: a stable CSS selector such as `.new-todo`, `#toggle-all`, `button.clear-completed`; mobile: the visible label) while `testId` stays the hook every port adds. The inventory also collects HTML `id="…"` values, the spec prompt and repair round ask for selectors where hooks are missing (the repair round used to be skipped exactly when the source had no hooks), the web executor tries the selector first and `[class~="<testId>"]` last, and source-mode Maestro flows use a plain-text selector as the text matcher. The first TodoMVC Vue observation verified 0/15 for want of this.
- Two elements of one screen with the same testId cannot be told apart by a flow: TodoMVC React tags both its new-todo field and its inline editor `text-input`, and the port's edit flows typed into the header field. The spec stage runs one repair round for such duplicates (`duplicateTestIds`: distinct ids for the port, the shared hook kept in a scoped `sourceSelector`), the spec prompt says so up front, and the web resolver never falls back from a scoped selector to a shared id.
- The inventory collects the test hooks a source already exposes (`data-testid`, `testID`, `accessibilityIdentifier`, `testTag`, `@+id`) into `hints.testHooks`; the spec prompt lists them and the spec stage gives the worker one repair round for element testIds that match none. An invented id verifies nothing on the source (the cart fixture's first run observed 0 of 21 behaviors for exactly this reason).
- Core workers (extract, vectors, fix) may run the source platform's interpreter (`node`/`npx tsx` for web, `swift` for iOS, `kotlinc`/`java` for Android; `logicRunnerAllow` in adapters) so golden vectors can be recorded from the source's real output (`executed`) instead of read off the code (`derived`). The first cart run's worker wrote a Node vector generator and was denied `node`; that is why.
- `core.extract` gets 20% of the run budget plus one continuation of 15% when it runs out (the first cart run's worker finished the crate but hit its $6 cap before returning its output), and a rerun keeps a crate that a previous attempt left behind instead of re-scaffolding. `core.vectors` skips its worker when every planned function already has three or more vectors with at least one `executed`, and when its top-up worker fails (budget, turns) while every planned function already has vectors it succeeds with a warning and keeps extraction's sets instead of blocking the port (the first forced-core UIKit run lost a usable 166-vector set, 148 executed, that way); a second worker only re-derived what `node` had already produced.
- Generic web sources (`web-generic`) are observed from their production build: `build` runs, the known output folder whose `index.html` that build wrote (`dist`, `build`, `out`, …; an older template such as CRA's `public/index.html` does not count) is served by the harness's static server, and only when there is no build or it fails does the `dev`/`start` script run. webpack-dev-server ignores `PORT`, picks 8080, and `--open` pops a browser on the user's machine, which is how TodoMVC React's first observation timed out three times. `startDevServer` puts no-op `open`/`xdg-open` shims first on the child's PATH so no dev script can pop a browser on the user's machine, and probes the URL a tool announces (the readiness poll used to keep the requested port even after the URL pattern matched the real one).
- Scaffold smoke tests (`ScaffoldTest.kt`, `ScaffoldTests.swift`) assert the generated route table (non-empty, contains the root, distinct, trimmed ids) instead of `2 + 2 == 4`; the critic counted the placeholder as a test that tests nothing. Scaffold `MPF.md` files also require tappable text to carry a control role (`TextButton`/`Role.Button`, `.isButton`, `<button>`/`<a href>`), and the critic's parity-docs rubric says PORT.md is written after its review, so a missing PORT.md is no longer a finding.
- Maestro qualified taps (`tap` with `text` on a shared id) probe first and act once: `evalScript` clears `output.mpfTap`, one `runFlow` per shape sets it when its selector is visible, then exactly one gesture runs for the shape found (a chain of "if visible then tap" branches evaluated in sequence fired a second time after a double tap swapped the label for an editor, which is how the React port lost 8 flows). The shapes, nearest first: the node carrying the text (iOS flattens rows), the node with the text on a descendant (an Android row container), then the control nearest to the text on its left and on its right (`leftOf`/`rightOf`; Maestro sorts relative matches by distance), because a Compose checkbox or delete button is a sibling of the row's label, not its ancestor (the corrected TodoMVC port failed 8 of 15 flows on exactly this). The scroll before such a tap looks for the text, not the control. Scaffold `MPF.md` files also ask that per-row controls carry an accessible name with the row's text, which makes the direct match work and is what assistive technology needs anyway.
- Web executor navigation: a `navigate` or `openRoute` whose URL differs from the open page only by its hash sets `location.hash` instead of reloading, because hash-routed apps keep in-memory state across a fragment change and a reload empties them (TodoMVC Vue's unknown-route behavior failed on exactly this). A different path or origin is still a full `page.goto`.
- Web executor, learned on TodoMVC (hookless Vue source, 0/15 verified at first): a `type` text ending in `\n` is filled and then submitted with Enter (fields without a button commit that way; Maestro already pressed Enter per line); a text qualifier on a leaf control (a row's checkbox, delete button) narrows the ancestor part of its descendant selector by the text, then descends, with a `li, tr, [role=row]` fallback for hook-based ids; `expectText` on a repeated element passes when any match carries the text; `expectCount` counts every match (`resolveAll`), since `resolveElement` narrows to the first; clicks recover from hover-only controls (hover the row), label-covered checkboxes (click `label[for]`), and finally force. Behaviors have `doubleTap` and `longPress` steps (`dblclick` / held click on web, `doubleTapOn` / `longPressOn` in Maestro) because TodoMVC-style inline edit opens on double click and a single `tap` can never verify it.
- Web executor step semantics: `type` on a `<select>` chooses an option (by value, then by label) instead of typing; `expectCount` accepts either N elements with the id or one container with the id holding N rows/items (`tr`, `li`, or direct children), because specs use it both ways.
- ESLint (Nuxt's config) honors `.gitignore`, so the Rust pattern `**/target/` silently excluded `packages/adapters/src/target/` from lint; `.gitignore` re-includes that directory with a negation. If a file reports "ignored because of a matching ignore pattern", check `.gitignore` first.
- Specs write templated test ids for repeated rows (`line-total-<SKU>`); the web resolver falls back to a `data-testid` prefix match and the Maestro compiler turns the placeholder into `.*` (Maestro ids are regexes). The cart run failed four web flows on exactly this before the fallback existed.
- Compiled Maestro flows scroll each target into view (`scrollUntilVisible`, optional) before tapping, typing, or asserting on it, because lazy lists hide lower rows on a phone, and a `type` step on a `picker` element opens it and taps the option whose text contains the value. The web executor mirrors both (select elements take an option; Playwright scrolls on its own).
- A stage left `running` by a process that died (a killed `run-control` driver, a daemon restart) is requeued by `Orchestrator.start` in the next process, attempt count intact, with a warn log; before this, `resume` reported "no runnable stages and the run is not settled" and stopped. The machine allows `requeue` from `running` and `queued` for that reason only.
- The critic's role text says compiled-flow gaps (custom steps, un-indexed expectCount, seeds) are factory limitations to report as advisory, never blocking: on the Java-to-iOS retest the critic blocked on the B-005 flow's skipped custom tap, which no fix worker can change, and spent a fix round on it.
- A critic escalation is answered with any non-reject choice (`accept` from the dashboard, `approve` from a script or the CLI); the critique stage treats all of them as "accept the remaining findings as deviations", records them in its result, and the report marks them `(accepted)`. Before this, `approve` reran the critic ($2 a round) and escalated again on the same finding.
- A flow with a step the compiler could not express (a `custom` step, an unhooked check on a source app) is partial: when it fails, the test stage reports it but does not count it as blocking, does not retry it for flakiness, and does not spend a fix round on it (the Java-to-iOS run burned both fix rounds and lost its critic on exactly such a hole). The flake retry reruns only the flows that failed, not the whole suite.
- Objective-C sources: identifiers are `@"…"` literals, setters (`setAccessibilityIdentifier:`), or `[NSString stringWithFormat:@"row-%ld", …]` (normalized to `row-<arg>`), and persistence is `NSUserDefaults`; the inventory matches all of them. When a source yields no hooks at all the spec stage warns instead of silently skipping the id check (the first Objective-C run verified 0/12 for that reason).
- Android Views fixtures and sources on targetSdk 35+: edge-to-edge enforcement puts an AppCompat action bar over the content, so the first button sits under the bar and no tap reaches it. `android:windowOptOutEdgeToEdgeEnforcement` does nothing for apps targeting SDK 36 (measured: the button stayed under the bar); `android:fitsSystemWindows="true"` on each root layout does the job (content starts below the action bar at y=283 on the emulator). The Java fixture does that; a real source that handles no insets is a genuine app defect the observe stage will report.
- A behavior's `screen` is where its flow opens (a deep link or launch argument on a target, a walk from the root on a source), so its first element step must belong to that screen; `validateBehaviorRefs` flags a mismatch for the repair round and the behaviors prompt says to set `screen` or begin with `navigate`. The third Objective-C pass lost eight flows to behaviors whose `screen` was the editor while their steps began on the list: the compiler walked to the editor and the first assertion failed, and the row flows never created the note they then looked for.
- Behavior steps: `tap` takes an optional `text` qualifier for rows that share a hook (Maestro tries `tapOn` with `id` plus `text` when visible, else `id` plus `containsDescendants`, because iOS flattens a row's labels onto the row and Android keeps them on children; Playwright uses `hasText`); with positional row ids the index already selects the row and the prompt says not to add `text` (the last Objective-C failure tapped `note-row-0` qualified by a title that had moved to row 1), so a worker never needs a `custom` step for a tap. The compiler tracks the current screen on target apps too, so `restart` relaunches into the screen the user is on (a tap on an edge trigger moves the tracker) and waits for `mpf-root` before `stopApp` so a seed or an edit is persisted first; scaffolds persist seeds synchronously (`UserDefaults.synchronize()`, blocking DataStore writes, synchronous `localStorage`). `wait` is a plain pause (an optional wait for an id that never appears) that works on source apps. `expectCount` compiles as "row N-1 visible and row N absent": by id when the rows carry an index (`note-row-0`, `note-row-<index>`), otherwise with Maestro's `index` selector on the shared id (the TodoMVC port marked 12 of 15 flows partial because un-indexed counts were recorded as holes); only a source app whose rows have no hook stays unverifiable.
- Android: a stale system dialog on the emulator (an "isn't responding" ANR, a crash dialog, the "Open with" chooser) makes every flow fail with "Element not found" against a healthy app. `dismissSystemDialogs` in the harness reads `dumpsys window` (plus `dumpsys window displays` on API 35+, where the focus line moved, and `dumpsys activity processes` for the error state), presses BACK, and force-stops the offending package unless it is the app under test; `launchAndCheck` runs it before every launch and the observe stage and Android adapter log what was cleared. The evidence summary now leads with `A system dialog covers the app: "…" (buttons: …)` instead of "nothing tagged". iOS has no equivalent without a UI driver (`simctl` cannot see SpringBoard alerts), so the launch-argument navigation and simulator shutdown remain the mitigation.
- Maestro's Android `hideKeyboard` is an unconditional BACK key (`input keyevent 4` in `AndroidDriver.kt`): when the keyboard is already closed (an Enter that committed the field closes it), it backs out of a single-activity app and every later step fails against the launcher (the TodoMVC React port lost all 16 flows this way while the Vue port survived only because its field kept the keyboard open). The compiler therefore dismisses the keyboard on Android only inside `runFlow: when: visible: {id: ".*inputmethod.*"}` (the IME's nodes are in Maestro's hierarchy) and keeps the optional `hideKeyboard` on iOS; both target adapters pass `platform` to the compiler now, which `platformBack` also needs.
- Maestro `inputText` types characters only: a `\n` inside a `type` step is dropped on Android (the UIKit-to-Android port's B-004 saw "Buy milkthen bread") and unreliable on iOS, so `inputLines` in the compiler types multi-line text line by line with `pressKey: Enter` between the lines.
- Workers may not use `Workflow`, `Agent`, or `Task` (fan-out stays with the orchestrator) nor the network; `cd <workspace> && …` is allowed and judged on the command after the `cd`. `for … do … done` loops are judged by their body wherever they sit in a line (a fix worker's `ls; for f in $(ls | sort); do …` was denied as a command named `for`). Every worker's allowlist includes the read-only text tools (`sed -n`, `awk`, `sort`, `cut`, `diff`, …): a fix worker was denied `sed -n … maestro.log | grep …` and burned turns guessing. The sandbox judges every command in a `for` loop or a `;`/`&&`/`||` sequence on its own, skips leading `NAME=value` assignments (`S=/path; ls $S`) while still scanning their paths, and lets core workers run `rustc --print`, `env`, and `printenv` (the first forced-core extraction lost turns on each of these). Workers that may write their workspace (generate, fix, core) also get `WRITE_BASH`: `mkdir`, `touch`, `mv`, `cp`, `rm` on relative paths only, so `mv probe.swift main.swift` works while `rm -rf /` or `cp x /tmp/y` never match (the critic stays read-only). The absolute-path scan only counts paths with two or more plain segments that are not preceded by `:` or `/`, so URLs, `/?query`, and regex fragments like `/g` pass.

- Source-app flows (`navigation: 'none'`): a behavior's leading `navigate` step, not its `screen`, says where the flow starts (the first UIKit run walked root -> editor -> root before every step because `screen` was the editor). Spec workers write edge triggers as prose ("Tap the `add-note` bar button"); `triggerElement` resolves a trigger to the element it names on the `from` screen and the spec prompt asks for ids. Elements whose testId matches no source hook (`hookMatcher` over the inventory's `testHooks`; a placeholder such as `note-row-<row>` stands for digits, an uppercase token, or another placeholder, never for lowercase words like `note-row-swipe-delete`) are asserted by visible text or left unverifiable, never matched by an invented id. The compiler tracks which screen the user is on across `tap` steps that trigger an edge, so a later `navigate` walks from there, and a return to the previous screen prefers a back edge (`back`, "back button", an element named back) over a forward edge such as save; a back edge with no hook compiles to Android's `back` or a tap on iOS's `BackButton` (`platform` in `MaestroOptions`).
- The inventory's hook regexes must cover every form a platform uses: UIKit sets `accessibilityIdentifier = "…"` (assignment, not the SwiftUI modifier call), Compose has `semantics { testTag = "…" }`. With an empty hook list the spec invents every id and observation verifies nothing. Interpolations (`\(indexPath.row)`, `${id}`) are normalized to `<…>` placeholders.
- esbuild rewrites `node:sqlite` to `sqlite` inside the tsup bundle, so the store loads it with `process.getBuiltinModule('node:sqlite')` and throws a plain "needs Node 22.13" error where the module is still behind a flag.
- The published CLI (`@multiplat/factory`) inlines every `@mpf/*` package (tsup `noExternal`), so those are devDependencies and their third-party runtime deps must be declared in `apps/cli/package.json` (`apps/cli/test/deps.test.ts` guards it). `scripts/bundle-dashboard.mjs` copies the static dashboard to `dist/dashboard`; tsup must not add a shebang banner because `src/main.ts` already has one.
- `DetectContext.files` stops at depth 2. Mobile language and UI-toolkit detection walks the tree (`sourceFiles` in `source/mobile.ts`) because Java, Kotlin, and Swift sources sit under package directories.
- Java-only Android apps on AGP 8.13: appcompat pulls kotlin-stdlib 1.8 next to kotlin-stdlib-jdk7/jdk8 1.6 and the build fails on duplicate classes; `implementation platform('org.jetbrains.kotlin:kotlin-bom:1.8.22')` lines them up (see `fixtures/inhouse/android-views-java-notes`).
- XcodeGen unit-test targets in Objective-C need `HEADER_SEARCH_PATHS: $(SRCROOT)/Sources` to import the app's headers; Swift tests use `@testable import`.
