# Adapters

All platform- and framework-specific knowledge lives in `packages/adapters`. The orchestrator, analyzer, critic, and dashboard never branch on a framework name; they work from the framework-neutral `AppSpec`, `BehaviorSpec`, and `PortPlan` in `packages/core/src/schemas`.

## Source adapters

A source adapter recognizes one kind of project and knows how to run it for observation. Interface: `SourceAdapter` in `packages/adapters/src/types.ts`.

| Member                                | Required | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`, `platform`                      | yes      | The adapter id recorded in the detection (`web-vite`, `ios-xcode`, ...) and the source platform (`web`, `ios`, `android`).                                                                                                                                                                                                                                                                                                                                                        |
| `detect(ctx)`                         | yes      | Returns a `Detection` with a confidence `score` (0..1) and `evidence`, or `undefined`. Never throws. Specific frameworks score higher (0.95) than generic fallbacks (0.5). Set `supported: false` with `unsupportedReason` to recognize a project the factory cannot port. When two detections score within 0.05 of each other, the ingest stage logs them and takes the best.                                                                                                    |
| `hints(ctx, detection)`               | no       | Framework-specific pointers for the analysis workers (`AnalysisHints`): entry files, where screens live, how navigation works, which persistence APIs to expect. Plain-language `notes` are passed to the LLM verbatim. The inventory fills `testHooks` itself from the source.                                                                                                                                                                                                   |
| `observe(ctx, detection, opts)`       | no       | Installs dependencies if needed and starts the app on `opts.port`, returning `{ url, stop }`. Web adapters use `startDevServer` or `serveStaticDir` from `@mpf/harness`. The observe stage then drives Chromium against the URL.                                                                                                                                                                                                                                                  |
| `observeMobile(ctx, detection, opts)` | no       | Builds a mobile source app for a simulator or emulator and returns `{ platform, appId, product, env, notes }` (`MobileSourceApp`), or `undefined` with a logged reason. The observe stage installs it, checks it stays alive, and walks the behaviors with Maestro flows compiled in `navigation: 'none'` mode (clean launch, taps along the AppSpec's navigation edges, typing, assertions, restarts). Behaviors that need seeds or deep links are unverifiable on a source app. |
| `existingTests(ctx, opts)`            | no       | The project's own test suite as a command (`command`, `args`, `cwd?`, `env?`, `timeoutMs?`) plus a `summarize` step that turns its output into a `TestOutcome`. The observe stage runs it once (after the flows, on the booted simulator or emulator for mobile sources, passed as `opts.device`) and records it as the `source` test result shown in `PORT.md` and on the dashboard's tests page: the baseline the ported tests are measured against.                            |

Without `observe` or `observeMobile`, the observe stage skips with a reason and behaviors stay unverified.

`DetectContext` gives a shallow listing (depth 2, build folders excluded), lazy `read(rel)`, `exists(rel)`, the parsed `package.json`, and merged `deps`. Mobile adapters walk deeper themselves because Swift, Kotlin, and Java sources sit several directories down.

Built-in source adapters (`packages/adapters/src/source/`):

- Web (`web.ts`): `web-next`, `web-nuxt`, `web-sveltekit`, `web-angular`, `web-vite` (React, Vue, Svelte, Solid, Preact, Lit, vanilla), `web-generic` (any package.json with a dev or start script), `web-static` (index.html, no build scripts). All of them observe through a dev server (or a static file server; `web-generic` first runs the `build` script and serves its output folder statically, falling back to the dev script only when there is no build or it fails) and run the `package.json` `test` script with `CI=1` as the existing tests (vitest gets `--run`; counts are parsed from vitest, jest, mocha, and `node:test` output).
- iOS (`mobile.ts`): `ios-xcode` (SwiftUI, UIKit, mixed; Swift or Objective-C) builds for the simulator with `xcodebuild` and runs `xcodebuild test` when a `*Tests` target exists, skipping `*UITests` targets; it accepts a `.xcworkspace`, a `.xcodeproj`, or a checked-in XcodeGen `project.yml`, which is generated into a project on first use in the run's copy of the source (needs `xcodegen`). `ios-swiftpm` gives hints and runs `swift test` when a `Tests` directory exists; it does not build for observation.
- Android (`mobile.ts`): `android-gradle` (Compose or Views; Kotlin or Java; multi-module) builds with `./gradlew assembleDebug` (or `gradle` on PATH), reads the application id with `aapt2 dump badging`, and runs `testDebugUnitTest` (the umbrella `test` task when product flavors exist).
- Cross-platform (`cross.ts`): `cross-flutter`, `cross-react-native`, `cross-capacitor` are recognized and refused with a clear message.

On a source app the Maestro compiler matches an element by its test id only when the inventory found that hook in the source (`hints.testHooks`: `data-testid`, `testID`, `accessibilityIdentifier`, `testTag`, `testId`, `android:id`). An element without a hook is matched by its label as visible text where the step allows it (`tap`, `expectVisible`, `expectHidden`, `expectText`, `swipe`); `type` and `select` need a hook, and the behavior is otherwise unverifiable with the reason.

### Adding one

1. Create or extend a file under `packages/adapters/src/source/` exporting a `SourceAdapter`.
2. Register it in `packages/adapters/src/registry.ts` (order matters only for ties; scores decide).
3. Add a detection test to `packages/adapters/test/detect.test.ts` using a synthetic project.
4. Add a pinned public fixture to `fixtures/manifest.json` with `expect.adapterId` (plus `framework`, `language`, or `webFramework` when they matter; `packages/adapters/test/fixture-matrix.test.ts` checks every synced entry), or an in-house fixture under `fixtures/inhouse/` listed in the manifest's `inhouse` array with the `adapterId`, `framework`, and `language` it must detect (`detect.test.ts` checks every entry).
5. If the adapter can run the app, implement `observe` (web) or `observeMobile` (simulator or emulator) and confirm the observe stage verifies the fixture's behaviors. Implement `existingTests` when the project has a conventional test runner so runs start from a known baseline.

## Target adapters

A target adapter owns one platform end to end. Interface: `TargetAdapter` in `packages/adapters/src/types.ts`.

| Member                   | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`, `target`           | The adapter id (`android-compose`, `ios-swiftui`, `web-vite`) and the target it serves; `getTargetAdapter(target)` in `src/target/registry.ts` picks by target.                                                                                                                                                                                                                                                                                              |
| `available(config, env)` | Whether the host can build and test this target now, plus the resolved environment (`JAVA_HOME`, `ANDROID_HOME`, `DEVELOPER_DIR`) that every command and the generation worker receive. A target that is not available is skipped with the reason.                                                                                                                                                                                                           |
| `scaffold(ctx)`          | Writes a green project: it builds before any LLM edits it. Conventions the worker must keep go in the project's `MPF.md`. When `ctx.core` is present the scaffold embeds the shared core (below).                                                                                                                                                                                                                                                            |
| `workerPrompt(ctx)`      | Conventions appended to the generation worker's system prompt (routes, deep links, test hooks, store, seed extra, the screens and test ids to implement, the core binding to call).                                                                                                                                                                                                                                                                          |
| `bashAllow`              | Commands the worker may run (build tool plus test runner); the generic stages add the read-only shell allowlist. The sandbox policy in `packages/llm/src/permissions.ts` also blocks `..` and `~` paths and absolute paths outside the workspace and read dirs.                                                                                                                                                                                              |
| `build(ctx)`             | Runs the build and parses diagnostics into `Diagnostic[]` for the fix loop; returns the product path, duration, and a log tail.                                                                                                                                                                                                                                                                                                                              |
| `unitTest(ctx)`          | Runs unit tests and parses JUnit-style reports into a `TestOutcome` (this is where the core parity test runs when a core is embedded).                                                                                                                                                                                                                                                                                                                       |
| `compileFlows(ctx)`      | Turns `BehaviorSpec` steps into platform flows deterministically: Maestro YAML on mobile (`compileMaestroFlow` in `src/target/maestro.ts`), a `flows/<id>.json` copy of the behavior on web that the Playwright executor (`src/target/web/executor.ts`) runs. A behavior that cannot be expressed comes back without a `path`; a flow that compiled with notes (custom steps, `expectCount` on Maestro) keeps its `path` and carries them in `unverifiable`. |
| `e2e(ctx, flows)`        | Installs, launches with a crash check, screenshots every screen (deep link on Android, `mpf_route` relaunch on iOS, hash route on web), runs the flows. Mobile adapters run Maestro with `--debug-output <workspace>/maestro-debug` and call `attachFlowEvidence` on failing cases so the fix worker gets the screenshot and a hierarchy summary. The web adapter also fails the launch check on any page error or console error.                            |
| `docs(ctx)` (optional)   | Build, unit-test, and e2e commands, the product path, and conventions a maintainer should know; the report stage prints them in each target's `PORT.md`. The optional `shipped` layout (the app id read from a workspace file, file groups, exclusions) feeds the PORT.md header and its "What shipped" file map.                                                                                                                                            |

The step vocabulary a compiler has to cover is `navigate`, `openRoute`, `tap`, `doubleTap`, `longPress`, `type`, `select`, `swipe`, `expectVisible`, `expectHidden`, `expectText`, `expectCount`, `restart`, `seed`, `wait`, and `custom` (`packages/core/src/schemas/behaviorspec.ts`). Two steps have known limits: `swipe` has no web gesture (the executor records a note and the port exposes the same action as a visible control), and `expectCount` has no Maestro equivalent. `custom` steps are notes, never stops: the typed steps around them still run. Multi-line text is typed line by line with an Enter press between the lines, because `inputText` drops newlines on Android. Templated ids for repeated rows (`line-total-<SKU>`) become a `.*` regex on Maestro and a `data-testid` prefix match on web.

Built-in (`packages/adapters/src/target/<platform>/{index,template}.ts`):

- `android-compose`: Kotlin, Jetpack Compose, Navigation Compose with `mpf://<applicationId>/<screenId>` deep links (the host qualifies the scheme so several ported apps on one device never share an implicit intent), `testTag` = AppSpec `testId` with `testTagsAsResourceId`, DataStore-backed `AppStore` with the source's keys, a debug `mpf_seed` intent extra, `safeDrawingPadding()` around the content, Gradle wrapper and the AndroidX train pinned in `ANDROID_VERSIONS`. Flows navigate by deep link.
- `ios-swiftui`: XcodeGen `project.yml`, SwiftUI with a `Router` over `NavigationStack`, `accessibilityIdentifier` = AppSpec `testId`, UserDefaults-backed `AppStore`, `mpf_seed` and `mpf_route` launch values. Flows navigate by relaunching with the route argument because external URL opens show a system dialog on the simulator. Requires a full Xcode (found through `DEVELOPER_DIR` or `xcode-select`) and `xcodegen`.
- `web-vite`: Vite + TypeScript, vanilla DOM, React 19, Vue 3, or Svelte 5, chosen from `run.options.webFramework` or the plan's `uiFramework` (anything else falls back to vanilla); hash router where `#/<screenId>` is the deep link, `data-testid` = AppSpec `testId`, localStorage-backed `store.ts` with the source's keys, a dev-only `?mpf_seed=<json>` query. Flows run through the shared Playwright executor against `vite preview`; the same executor verifies behaviors on web source apps in the observe stage.

### Embedding the shared core

When the plan enabled a shared core and `core.build` succeeded, `ctx.core` carries the built module, its manifest, and the vectors directory (`CoreHandoff`). A target adapter embeds it in `scaffold` with `writeCoreEmbed(workspace, ctx.core, <embed>)`, where the embed comes from `webCoreEmbed`, `androidCoreEmbed`, or `iosCoreEmbed` in `src/core/`: a copy of `mpf_core.wasm`, a generated host binding (TypeScript, Kotlin on Chicory 1.7.5, Swift on WasmKit 0.4.0), the vector files, and a parity test that the target's normal unit-test command runs. The Android template raises `minSdk` to 28 and the iOS template raises the deployment target to iOS 18 only when a core is embedded. The worker prompt gets the matching `*CoreConventions` section so the generated app calls the binding instead of reimplementing the logic. A new target follows the same pattern with a binding generator that speaks the ABI in `docs/ABI.md`.

The orchestrator's `generate`, `build`, and `test` stages (`packages/orchestrator/src/stages/target.ts`) are generic: they pick the adapter by `stage.target`, resume the generation worker's session for bounded build-fix (3) and test-fix (2) rounds, retry failing must-behaviors once to separate flaky from real, and block with `build-error` or `test-failure` when the budget of rounds runs out. The `critique` and `fix` stages (`stages/critic.ts`) and the `report` stage (`stages/report.ts`) are generic in the same way.

## Rules

- No hardcoded machine paths. Discover toolchains through `mpf doctor` checks in `packages/harness/src/toolchain`.
- No user-specific defaults. A fixture from one person's machine is never the basis for a template.
- Adapters must degrade honestly: skip with a reason rather than pretend to succeed.
